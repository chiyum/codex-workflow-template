# 工程知識庫寫入與查找規則

本目錄保存跨專案可複用的工程教訓。日常入口是 `ROUTER.md`；`INDEX.md` 是完整相容索引。本檔是知識卡查找、合併、狀態與分流規則的權威來源。

## 先查再寫

1. 先從本次症狀辨識 `problem-class` 與 `tech`，讀 `ROUTER.md` 命中的 playbook。
2. 沒有命中時，以 `rg` 同時搜尋 `INDEX.md`、卡名與 frontmatter，例如：
   ```bash
   rg -n 'problem-class:.*<問題類別>|tech:.*<技術>' ~/.codex/knowledge/INDEX.md ~/.codex/knowledge/*.md
   ```
3. 只讀最相關的 1–3 張卡，比對根因、適用條件與對策。標籤相同不代表可合併；只有根因與適用條件相同時，才把新證據、來源與日期併入既有卡。
4. 根因或適用條件不同時保留獨立卡，並以「關聯」互相連結，避免把相似症狀硬併成錯誤規則。

## 寫入與索引

- 命中既有卡時，重讀最新內容後做語意聯集；保留不同產品的來源、日期、本機重現與相反證據，不以 mtime 或整檔覆蓋決勝。
- 確實沒有可合併卡時才新增。新卡預設 `status: proposed`，使用六段格式：症狀、根因、對策、程式碼參考、適用／不適用、關聯。
- 新增卡或讓既有卡涵蓋新的可查找主題時，同步更新 `INDEX.md`；命中既有 playbook 時也更新其速查或檢查清單。`ROUTER.md` 只在新增技術域 playbook 時加路由。
- 寫入前重讀目標檔；共享工作樹有新變更時重新合併，不覆蓋其他 session。

## status 與證據

- `proposed`：agent 推論、本機重現或尚未取得線上／使用者裁決證據；也是新增卡的預設值。
- `validated`：必須在正文附使用者明確決定，或可定位的線上實證來源（run、evidence、部署後紀錄等）。只有欄位存在、測試通過或 agent 自行判定都不足以升級。
- 整理既有 `validated` 時先查正文與來源證據；查無合格證據才降為 `proposed`，並在卡內留下降級原因，不刪除原始觀察。

## 技術知識與流程提案

- 能直接幫助產品工程判斷症狀、根因、對策或適用條件的內容，包括測試、fixture、migration 與回歸測試教訓，留在日常技術路由。
- 只有針對 Codex harness、角色、gate、evidence 儀式或工作流本身的改善建議，才放進 `knowledge/harness/`，作為 retro 的提案輸入。
- harness 提案不因被記錄就自動成為 gate；要改工作流或新增阻擋條件，仍須經需求凍結與核准流程。
- `archive/` 只保存不再作日常輸入的歷史內容；不得用搬入 `archive/` 或 `harness/` 的方式充當知識收斂。
